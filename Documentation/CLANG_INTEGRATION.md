# Embedded Clang Integration

The native bridge does not launch a `clang` executable. A host application can
link Clang/LLVM libraries and register an in-process driver entry point.

## Current driver entry point

Current Clang exposes `clang_main` from its driver implementation with an
`llvm::ToolContext`.

The reference adapter:

1. prepends `clang` as argv[0],
2. forwards the remaining arguments generated by XtoolMobileKit,
3. constructs a ToolContext,
4. calls `clang_main`,
5. returns the resulting exit code to the Swift layer.

## NativeToolchainSupport

The built-in C++ target supports:

```
XTOOL_ENABLE_EMBEDDED_CLANG=1
```

when the consuming build provides compatible Clang/LLVM headers and libraries.

Default SwiftPM builds leave this disabled so XtoolMobileKit remains buildable
without a multi-gigabyte LLVM dependency.

## Host-owned integration

`Support/ClangAdapter.cpp` is the standalone integration path. Compile it in a
host target that owns the Clang/LLVM linkage and call:

```c
xtool_register_host_clang();
```

The callback is then visible through
`XtoolNativeCompilerBridge.currentCapabilities`.

## iOS considerations

The adapter does not call `Process`, `posix_spawn`, or a shell. Inputs and
outputs should use absolute sandbox paths. The compiler libraries themselves
must be linked into the application build.
